> 擴寫自 2026-08-18 的 HackMD 調查報告（家用網路 192.168.1.0/24 拓撲調查，單日完成）。內網 IP 保留、SSID 與帳密類細節不公開。

## 我家的網路圖，是三年前畫的

事情是這樣開始的：翻出一疊舊紙本紀錄，上面畫著家裡的網路拓撲——但那是 ADSL 時代寫的了。數據機到底換過沒、AP 掛在哪個 IP、那台「3F 的小黑盤」到底是什麼，記憶和紙本互相矛盾。更麻煩的是，家裡還有一條 **2.4G 網橋把整個 /24 L2 互橋到外婆家（同家庭的自家房產）**，等於廣播域的邊界比一般家庭更模糊。

與其繼續猜，不如花一個下午把整個網段翻過來查一遍。這篇文章記錄完整流程：**ping sweep → ARP 表 → OUI 廠商查詢 → HTTP 探測 → 授權 SSH 實證**，每一步都有可複製的指令，最後附上發現的問題與修繕建議。如果你也有一張「不知道多久沒更新」的家用網路圖，這套流程可以直接搬走。

## 方法總覽

整個稽查的核心邏輯很簡單：

1. **先 ping 過一輪**，逼出 ARP 表——ARP 表就是這個廣播域的「在場證明」；
2. **用 MAC 的 OUI 前綴查廠商**，一個前綴通常足以辨識裝置是誰家的（Zyxel、TP-Link、Nintendo……）；
3. **對開著 web 管理面的裝置探 HTTP title**，確認身份；
4. **對自己有管理權的機器直接 SSH 進去**，用 `ip addr` / `ifconfig` 拿到不可抵賴的實證；
5. 最後**拿實測結果勘誤舊紀錄**，把不確定的項目列成清單。

重點觀念：**前三步都是被動偵測，只能「推定」；只有登入裝置本身的輸出才是「實證」**。推定與實證要明確分開記。

## 步驟一：ping sweep 與 ARP 普查

從管理機（與目標同 L2）先掃一輪：

```bash
# ping sweep：-sn 只做 host discovery，不打 port
nmap -sn 192.168.1.0/24
```

跑完立刻看 ARP 表——nmap 的 host discovery 會把回應過的主機灌進鄰居表：

```bash
ip neigh show
```

輸出會是一串 `IP dev lladdr [REACHABLE/STALE]` 的列表。這一步的產出就是本次稽查的骨幹：**誰在線、誰的 MAC 是什麼**。手機、筆電這類家庭終端會隨在線狀態浮浮沉沉，所以我只把「網路設備」（AP、網橋、VM、伺服器）當成普查對象，終端裝置標記為快照即可。

## 步驟二：OUI 查廠商

拿到 MAC 後，把前 three bytes（OUI）丟去查廠商。懶人做法是直接打 maclookup 的 API：

```bash
curl -s "https://api.maclookup.app/v2/macs/00:eb:d8:04:5e:5f" | jq -r '.company'
# MERCUSYS TECHNOLOGIES CO., LTD.
```

也可以到 [IEEE 的 OUI 資料庫](https://standards-oui.ieee.org/) 手動查。這一步的辨識力比想像中強：例如看到 `bc:24:11` 開頭就知道是 **Proxmox VM 的預設 MAC 前綴**——那不是實體機，是某台 PVE 上開出來的虛擬機；看到兩個裝置同屬 Zyxel OUI，就會聯想到它們是同一套系統的零件。

普查結果整理成表（IP 尾碼寫法）：

| IP | OUI / MAC 特徵 | 身份 |
|---|---|---|
| `.1` | Zyxel | 數據機（閘道/DHCP） |
| `.105` | TP-Link | 外婆家 AP（經網橋） |
| `.109` | Nintendo | 客廳遊戲機 |
| `.126` | Mercusys | 客廳 AP（bridge） |
| `.127` | ASUSTek | 書房 AP（bridge） |
| `.147` | Zyxel | 小黑盤（**推定**：同 OUI + 正常拿 DHCP） |
| `.154` | Proxmox VM MAC | OPNsense VM 的 WAN 側 |
| `.173` | KTC | 客廳 Android TV（推定） |
| `.185` | Intel | 未列管筆電類（推定） |
| `.195` | Apple | 家人裝置（推定） |
| `.200` | Juplink（RTL8125 貼牌） | PVE host 的 lifeline 介面 |
| `.251` | Mercury | 2.4G 網橋 |

## 步驟三：HTTP 探測確認管理面

網路設備幾乎都開 web 管理頁，對 80/443 探一下 title，身份就八九不離十：

```bash
# 找出有開 web 的主機
nmap -p80,443 --open -T4 192.168.1.0/24

# 對開著的主機抓 HTTP title（自簽憑證要 -k）
nmap -p80,443 --open --script http-title 192.168.1.0/24
# 或手動：
curl -ksI https://192.168.1.1 | head -n1
```

實測中數據機的管理頁是 **HTTPS only**（自簽憑證），兩台 AP 則各回各的管理頁面。順帶一提，這台中華電信數據機就是那台被 2025-09 行動條碼鎖擋住工程登入的機型——我之前[寫腳本繞行動條碼鎖](/blog/chunghwa-modem-qrcode-bypass/)講過這個機制；不過這次稽查我沒再動它，把「進不了工程模式」如實記為限制。

## 步驟四：SSH 實證（僅限自己的機器）

對自家 PVE 與 OPNsense 這種**本來就有 root 權限**的機器，別再推定了，直接進去拿實證：

```bash
# OPNsense：確認 WAN 側介面狀態與位址
ssh opnsense.ifconfig.local ifconfig vmbr0

# PVE：橋接介面、實體網卡狀態、鄰居表一次看
ssh pve 'ip -br addr; ip -br link; ip neigh'
```

這一步撈到三個關鍵事實：

1. `.154` 那個 Proxmox VM MAC **確定就是 OPNsense 的 WAN 側**（`vmbr0` 上掛的虛擬網卡），不是別的 VM；
2. 實體 I219 網卡當時是 `NO-CARRIER`——那是接在上面的工作站**暫時拔線**，不是故障。沒有這一步實證，很容易誤判成網卡壞掉；
3. OPNsense 的 WAN 側透過 RA 拿到了**全域 IPv6**——代表整個家用網段是有全域 v6 的，這在後面的安全備註會再提到。

## 步驟五：拿實測結果勘誤舊紀錄

這是整個稽查最有成就感的部分。舊紙本對了三件事，也錯了三件事：

- ✅ 拓撲骨架（數據機 + 兩台 bridge AP + 網橋）方向正確；
- ❌ 兩台 AP 都寫成同一個 IP `.105`——實測是 `.127` 與 `.126`，而 `.105` 其實是**外婆家那台 TP-Link**。這個混淆很危險：把外婆家 AP 誤當自家書房 AP，等於把信任邊界畫錯了；
- ❌ 紀錄中的舊型號（ADSL 時代數據機）早已汰換成光世代 GPON 機型，汰換時點無紀錄可考；
- ❌ 舊紀錄提到的某組內建 WiFi SSID 不存在——實際設定是另一組，且停用中。

**教訓：網路圖不是畫完就算，要定期用實測校準；而且校準時要以「當下實測」為準，不是以「記憶」為準。**

## 稽查後的發現與修繕建議

翻完整個 /24，我列了這幾條，按優先序：

### 1. 全部網路設備的 IP 都在 DHCP 上漂

兩台 AP、網橋、OPNsense WAN、小黑盤的管理 IP **全是浮動 DHCP、無 reservation**。這次普查的 IP 表只是快照，重開機後就會漂移。修法很直接：在數據機的 DHCP 設定裡對這幾個 MAC 做 reservation。可惜這台數據機的工程帳號被行動條碼鎖擋住，正規途徑是打 123 請中華電信處理——這是我目前唯一「想做但被鎖在外面」的項目。

### 2. 外婆家 AP 的弱 WiFi 密碼，是唯一的 L2 入口

先說清楚：網橋對端是外婆家（自家房產、同家庭），屬於同一信任網域，**不是**外部入侵點——一開始我還把這條列為首要疑慮，確認後解除。但剩下的問題很實際：那台 AP 的 WiFi 密碼強度低，而它**直接坐在家庭廣播域裡**。密碼被猜中，等於直接加入整個 `192.168.1.0/24`，包括 PVE 管理面。低成本收斂：**改一組強密碼，五分鐘的事**。

### 3. 沒有訪客隔離

客廳那台 AP 上掛了約 24 個無線用戶端，全部在同一個主網段，訪客網路功能沒開。訪客來了只能給主網段密碼。建議至少啟用訪客 SSID，把不受信任的裝置隔開。

### 4. IPv6 防火牆政策不可考

數據機會發 RA，終端可能拿全域 v6 直接對外。問題是 v6 防火牆政策在數據機上，而工程模式進不去——這條只能掛著，等哪天能進去了再確認。

### 5. 管理面一律走 overlay，不跟家用網段混流

雖然管理機和 PVE 在同一個 L2，我的 homelab 管理流量**全部走 Tailscale**（subnet router 廣播內部管理網段），家用網段的直連只留給家人的消費型服務。這是既有防護，這次稽查確認它仍然成立，就維持不變。

```text
管理機（Tailscale 100.x）
    ↓
OPNsense subnet router（廣播 homelab 管理網段）
    ↓
PVE / NAS / prod VM 的管理介面
```

## 踩雷與注意事項

- **bridge AP 的身份辨識要靠管理頁**：bridge 模式的 AP 從外面看不出角色（不 NAT、不發自己的網段），一定要登入管理頁確認模式，不能只看 IP 行為猜。
- **「同 OUI」不等於「同一台」**：小黑盤 `.147` 我標為「推定」，依據是與數據機同屬 Zyxel OUI 且正常從上游拿 DHCP，推測是全屋通套件的 repeater。這種推定要老實標「推定」，不要在筆記裡悄悄升級成「確認」。
- **終端裝置的快照會腐爛**：手機、遊戲機、電視的 IP 與在線狀態天天變，普查表要標註快照日期，別把「上次掃到的」當成「恆常存在的」。
- **先盤點再動手**：這次能單日完成，是因為一開始就列了待查清單（舊紀錄勘誤、小黑盤身份、埠位對應……），逐項打勾，而不是邊掃邊發散。
- **掃自家網段就好**：這套手法對 192.168.1.0/24 是稽查，對別人的網段就是探測。nmap 的授權邊界自己顧好。

## 結語

一個下午、五個步驟，把一張三年前的網路圖校準成「有實證的快照」，順手抓出三個配置錯誤和一個信任邊界誤記。這套流程沒有任何高深技術——`nmap -sn`、`ip neigh`、OUI 查詢、`curl -kI`——但組合起來的辨識力遠超乎直覺，尤其是 OUI：**一個 MAC 前綴就足以把「某個匿名 IP」變成「Nintendo 的遊戲機」**。

老實說，最難的不是技術，是「紙本紀錄過時了但沒人知道」這件事本身。建議把這次稽查的指令存成一個小腳本，每半年跑一次，diff 一下普查表——網路圖也是會腐爛的。
